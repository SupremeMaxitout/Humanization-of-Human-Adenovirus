# Docking methodology

## Why HADDOCK

HADDOCK (High Ambiguity Driven protein-protein DOCKing) is an
**information-driven** docking engine: instead of searching blindly, it takes
experimental or predicted knowledge about which residues form the interface and
uses that to bias the search.

That is the right fit here for three reasons.

**The interface is known, at least approximately.** Antibody paratopes,
Factor X binding sites and defensin contact regions are documented. Blind
docking of a ~950-residue trimer against an antibody wastes almost all its
sampling on regions that cannot be the answer. HADDOCK's ambiguous interaction
restraints (AIRs) let you say "these residues should be at the interface" and
concentrate sampling there.

**Flexible refinement.** HVRs are surface loops. Rigid-body docking alone
handles them badly. HADDOCK's three-stage protocol — rigid body, then
semi-flexible refinement of interface side chains and backbone, then explicit
water refinement — lets the loop adapt, which is exactly the physics of an
engineered loop meeting an antibody.

**The output is a ranked ensemble with clustering built in**, which is what a
comparative screen needs. You are not asking "does this bind"; you are asking
"does the humanised variant bind this immune component *less well than wild
type does*". That is a relative question, and clustering gives the statistics
to answer it.

The trade-off: HADDOCK needs interface information. If you have no idea where
the binding site is, a blind docking method is more honest.

## What the score is, and is not

```
HADDOCK score = 1.0·Evdw + 0.2·Eelec + 1.0·Edesolv + 0.1·Eair
```

| Term | Meaning |
|---|---|
| `Evdw` | van der Waals — shape complementarity |
| `Eelec` | electrostatics, down-weighted because it is noisy at an interface |
| `Edesolv` | empirical desolvation — cost of burying surface |
| `Eair` | restraint violation — penalises poses ignoring your AIRs |

More negative is better.

**It is an empirical ranking function, not a binding affinity.** It does not
give a Kd or a ΔG. It is calibrated to separate near-native poses from decoys
for *one* complex, not to compare different complexes.

Consequences you must respect:

- **Never compare scores across targets.** −120 against HD5 and −120 against
  Factor X do not mean equal binding. The report only ever compares within one
  target.
- **Never pool HADDOCK 2.5 and HADDOCK3 scores.** Different versions, different
  defaults. Every output here records which engine produced it.
- **A better score is a hypothesis, not a result.** It prioritises candidates
  for experimental testing.

## Why cluster scores, not the single best structure

A run produces hundreds of models. The single lowest-scoring one sits in the
tail of a distribution and is largely noise — rerun with a different seed and a
different structure wins.

What reproduces is a **cluster**: a group of models that converged on the same
binding mode. Clustering (FCC, fraction of common contacts) groups poses sharing
interface contacts. The pipeline ranks by:

```
cluster score = mean HADDOCK score of the best 4 members of the best cluster
```

and reports alongside it:

| Column | Why it matters |
|---|---|
| `cluster_size` | how many models found this mode. Large = reproducible. |
| `cluster_sd` | spread of the top members. Tight = converged. |
| `n_clusters` | many small clusters = sampling never converged; distrust the result. |
| `n_structures` | how many water-refined models exist at all. |

A cluster of 4 with a wide spread is weak evidence. A cluster of 40 with a tight
spread is strong. **Report both the score and the cluster size** — a score alone
hides the difference.

If no cluster analysis is present, the pipeline falls back to the mean of the
best 4 structures and records that in the `note` column.

## AIR files are your input, and your main assumption

Ambiguous Interaction Restraints tell HADDOCK which residues should contact.
They are **not generated by this pipeline** — you supply one per target,
typically from the [Bonvin lab web tools](https://wenmr.science.uu.nl/), from
literature interface data, or from a known complex structure.

```
assign (resid 42 and segid A) (resid 118 and segid B) 2.0 2.0 0.0
```

This is the single largest assumption in the whole docking stage. Wrong AIRs
give confidently wrong answers: HADDOCK will faithfully dock into whatever site
you specify. State in your methods where each AIR set came from.

The pre-flight (`00_check_inputs.py`) verifies each AIR file exists and contains
`assign` statements, but it cannot tell you whether the restraints are *right*.

## Single chain for docking, three chains for MD

The trimer is written twice by Tool 1, and this is not redundancy.

HADDOCK treats each input molecule as **one rigid body**. Hand it a three-chain
trimer and it docks three separate molecules, which is not what you want. So
docking uses the single-chain merged form.

MD is the opposite: merging protomers creates artificial peptide bonds across
the chain junctions, which stiffens the very inter-protomer interface an HVR
flexibility study measures. So MD uses the real three-chain form.

`00_check_inputs.py` fails the run if a docking input has more than one chain.

## Sampling

| Stage | Default | Purpose |
|---|---|---|
| `it0` | 1000 | rigid-body sampling |
| `it1` | 200 | semi-flexible refinement of the best it0 models |
| `water` | 200 | explicit water refinement — **these are the final structures** |

Defaults follow HADDOCK's own recommendations. Reduce for a quick pilot;
do not reduce for the run you report. Fewer it0 models means a worse chance of
finding the near-native mode at all.

Clustering defaults: `clust_cutoff = 7.5` (FCC), `clust_size = 4`.

## HADDOCK 2.5 vs HADDOCK3

Both are supported. They are **not interchangeable**.

| | HADDOCK 2.5 | HADDOCK3 |
|---|---|---|
| Interface | `run.param` + patched `run.cns` | modular `run.toml` |
| Availability | on request from the Bonvin lab; licences are personal | open source on GitHub |
| Output | `structures/it1/water/` | `haddock3_out/<NN_module>/` |
| Status here | the engine this project used | provided so others can reproduce without a licence |

Set `docking.engine` in the config. Every CSV, spreadsheet and manifest records
the engine used, and the report warns against pooling scores.

Both require **CNS** as the computational engine. CNS is free for non-profit use
but must be registered separately at <http://cns-online.org/v1.3/>. It is not
bundled here and cannot be redistributed.

## Operational lessons

Each of these cost a full queue cycle.

**Result collection must not inherit `set -e`.** In the original run, HADDOCK
finished successfully but `results/` stayed empty while `work_pbs/` held
everything — the first failed copy aborted the rest of the collection block.
Generated jobs now scope `set -e` to setup and docking only, and
`02_collect_results.py` exists to rescue runs regardless.

**The first `run_haddock.py` call exits non-zero by design.** It only generates
`run.cns`. Treating that as failure aborts every job. The generated scripts wrap
it in `set +e`.

**`$HOME` does not expand in PBS `-o` directives.** Use absolute paths, and
create the log directory before submitting, not inside the job.

**Job names must be short and sanitised.** PBS rejects long or unusual names;
the generator truncates to 15 characters and strips anything non-alphanumeric.

**Jobs are idempotent.** A pair with collected water-refined results is skipped,
so resubmitting the whole batch after a partial failure is always safe.
